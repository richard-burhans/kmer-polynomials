# KP-7 over CM31 with SIMD: AVX2 and AVX-512 on laila (2026-11-10)

**Verdict: the SIMD version nearly closes the gap. On laila's Xeon Gold 6330, the provable strand-symmetric hash over
CM31 runs at 0.87× ntHash with AVX2 (8 lanes) and 0.91× with AVX-512 (16 lanes). The best 61-bit version was 0.49×.
It needs about 60 instructions per k-mer against ntHash's 110, so the remaining gap is IPC (2.3 against 4.7), not
work.**

## Method

`hash/kp7m31.{h,c}` (24c82c1; bench methods 43c8e07). CM31 = F_{p²} = ℤ[i]/(p), p = 2³¹ − 1 (p ≡ 3 mod 4). The
construction is the same as kp7: A = 1, C = i, G = −i, T = −1; F = Σ s_t x^t; R = −x^{k−1} p(1/x); the hash is
(F + λ)(R + λ). x and λ are random complex values, so two distinct double-stranded k-mers collide with probability
≤ 2(k−1)/p² ≈ 1.3e-17 per pair at k = 31 (1.34e-17 for 2k/p²; corrected 2026-11-11 from "2k/p² ≈ 1.4e-17", round-1 adjudication L1 F2). The output is the 62-bit packed value re | im << 31. **This is a different
hash from the 61-bit kp7**, so its reference is a new scalar implementation.

Rolling uses the λ state and merged 16-entry tables (as in kp7.c): G' = G·x⁻¹ + tf[idx], H' = H·x + tr[idx], hash
= G·H. That is three F_{p²} products per k-mer.

SIMD, using the standard Mersenne-31 vector techniques (as in Plonky3's mersenne-31 AVX2/AVX-512 packing and the
Circle-STARK CM31 extension arithmetic; no code copied):
- 32-bit lanes. 32×32→64 products come from `mul_epu32` on the even lanes plus a copy shifted by 32 bits for the odd
  lanes.
- The real part is computed as a·c + p·2³¹ − b·d in 64 bits, so it never goes negative (every product is below
  p·2³¹). Mersenne folding (v & p) + (v >> 31) runs twice, then `min_epu32(t, t − p)` makes the result canonical.
- A lane-interleaved index pre-pass stores idx = code(out)·4 + code(in) as bytes, loaded per step with `vpmovzxbd`.
  The base code is (c >> 1) & 3 (A→0, C→1, T→2, G→3, either case).
- Table lookup uses `vpermd`. With AVX2 that is two registers plus a `blendv` on idx > 7; with AVX-512 it is a
  single `vpermd` over 16 entries.
- Each lane is a contiguous stretch of the block, as in kp7_sym_seq. The last lane finishes the remainder in scalar
  code. Blocks shorter than the lane count run scalar.

Tests (`test_kp7m31`, also run inside the laila job, so the AVX-512 path was exercised on AVX-512 hardware):
- rolling == direct at every window (N, lowercase, k = 1, 8 and 31)
- F(rc s) = R(s) and sym(s) = sym(rc s)
- one value per double-stranded class at k = 7 and 8 (8,192 and 32,896)
- scalar, AVX2 and AVX-512 `kp7m31_sym_seq` bit-identical to the reference roller, hashes and positions, for 4 N
  layouts and block sizes 1, 3, 5, 7, 8, 9, 15, 16, 17, 64 and 4,096

`make mutation` kills a broken odd-lane multiply and a broken blend threshold.

## Laila hardware counters

`cannabis-genome/scripts/laila_perf.py run --label kp7m31`, job 6eb67d389ce42771, one counted process per method
(`bench cs10.fa 31 1 throughput only=<method>`). Both libraries were built `-O3 -march=native` in the job, and a load-only
baseline ran in the same job (6.95e9 cycles, 20.75e9 instructions). The baseline was subtracted and the result divided
by 736,547,799 k-mers. Raw output: `laila_counters_m31_2026-11-10/`.

| method | cycles/k-mer | instructions/k-mer | IPC | vs ntHash |
|---|---|---|---|---|
| ntHash canonical | 23.5 | 110.1 | 4.69 | 1.00 |
| kp7 61-bit, `sym_seq` x real, 2 lanes (the previous best) | 47.7 | 179.3 | 3.76 | 0.49 |
| CM31 scalar | 76.0 | 236.3 | 3.11 | 0.31 |
| **CM31 AVX2, 8 lanes** | **27.0** | **61.7** | 2.28 | **0.87** |
| **CM31 AVX-512, 16 lanes** | **25.8** | **60.2** | 2.33 | **0.91** |

Local sanity run (a shared host, so ratios only): CM31 AVX2 223.2 M k-mers/s and CM31 scalar 86.1. The scalar and AVX2
hashes XOR'd to 0, so they are identical.

## Reading

- The SIMD loop does about half of ntHash's instructions per k-mer (60 against 110) but retires them at half the rate.
  AVX-512 barely beats AVX2 (25.8 against 27.0 cycles), so the vector arithmetic is not the bottleneck.
- The likely remaining costs, all outside the arithmetic:
  - packing each 62-bit output and storing it scalar, per lane, into a strided position (the vectors spill to a temp
    array and are read back, 8 or 16 stores per step)
  - the benchmark's per-hash callback, which ntHash pays too
  - the scalar index pre-pass
- Fairness: ntHash ran through its per-k-mer `roll()` API. Ours is a block API that writes buffers.
- AVX-512 IFMA (52-bit multiply-add) would not help M31: 32-bit lanes with mul_epu32 already suit a 31-bit prime.
  IFMA would matter for a prime near 2⁵².
