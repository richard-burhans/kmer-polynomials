# KP-7: batch symmetric hashing (2026-11-10)

**Verdict: the batch loop makes the symmetric hash 0.66× ntHash, up from 0.40×. With x real it runs at 158.7 M
k-mers/s: +39% over the best per-call version and +66% over the original. Bit-identical.**

Motivation: the cpu-clock profile of `kp7_roll_sym` (`bench … only=` under `perf record -e cpu-clock`, since this VM has
no hardware counters) put about 25% of the time in per-k-mer plumbing. That was 11% packing the rolling state into
and out of the roller struct, 7% call overhead, and 8% branches. `kp7_sym_batch` (hash/kp7.c, 19bc3a8) hashes
consecutive k-mers in one loop with the state in locals, writes them to a caller buffer (4,096 here), and checks for
N once per incoming base.

Run: `hash/run_bench.sh 31 5 throughput batch` on cs10, single thread, k = 31, 736.5 M k-mers, 5 interleaved rounds,
`-O3 -march=native` for kp7 and ntHash alike. Raw output: `kp7_rolling_vs_nthash_2026-11-10.throughput.batch.raw.txt`
(kp7 commit 19bc3a8, a clean tree). The benchmark printed "identical: yes" for every variant's hash XOR against the
plain symmetric hash. Tests compare hashes and positions for buffer sizes 1, 2, 7 and 4,096, and for every N layout.

| method | median M k-mers/s | 5 rounds | vs ntHash |
|---|---|---|---|
| ntHash canonical | 240.4 | 223.0–247.8 | 1.00 |
| original `kp7_roll64` symmetric, x real | 95.5 | 91.7–97.0 | 0.40 |
| `kp7_roll_sym` all three options, x real | 114.4 | 112.9–117.8 | 0.48 |
| **`kp7_sym_batch`, x real** | **158.7** | 137.5–162.3 | **0.66** |
| original symmetric, x complex | 85.1 | 82.3–86.3 | 0.35 |
| `kp7_roll_sym` λ-state + merged, x complex | 100.0 | 90.6–103.2 | 0.42 |
| **`kp7_sym_batch`, x complex** | **127.1** | 123.0–129.2 | **0.53** |

Both batch versions now beat the original per-call forward-only hash (124.2), even though they compute both strands
and the symmetric product. The batch loop with x complex, which has the stronger (k−1)/q² collision bound, is faster
than any per-call x-real version.

Remaining gap (0.66×): each k-mer still has a serial dependency chain (multiply, reduce, add) on each strand. Next:
interleave independent stretches of the sequence so the chains overlap (step 2), then Mersenne-31 SIMD (step 3).
Hardware counters on laila would show whether the loop is now latency-bound (low IPC).
